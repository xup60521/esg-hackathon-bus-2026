# 逐班重建可行性與有界分流情境

研究工作日：2026-11-04，Asia/Taipei。資料查核時間見 JSON 的 UTC 欄位。基準 HEAD 為 `5861d0651eed3c9bd898bd5fd76ab1d18c19de5f`。

## 摘要

現有資料庫保有車輛欄位與秒級配對上下車時間，可以做「同車輛值的同步票證區間」診斷。公開小時彙總沒有這些欄位，不能拿來重建逐班載客。全庫 1,800,910 筆旅次共有 122 個車輛欄位值，但欄位值是否對應唯一實體車、逐班容量及非票證涵蓋率，仍未獲營運資料驗證。

2025 年一月有 73,411 筆旅次。排除時間超長與同站旅次後，以車輛、支線、推定方向切出 3,450 個零間隔候選群組。站序回退及跨支線或方向的時間重疊確實存在，不能把這個數字當實際班次數。原型交付的是品質診斷與分流上限受參數限制的情境運算，不是可執行班表，也不是實測載客率提升。

本方向沒有修改 UI、路由、依賴或共享紀錄，沒有部署、提交或推送。

### 本機彙總

24 個 `data/midstop-months` 檔案與 `public/data/midstop.json` 經獨立合併逐鍵比對一致，共 292,562 列，上下車各 1,800,910 人次。未知方向上車 6,281 人次。欄位為日期、支線、方向、站點、小時、上車數與下車數，沒有車輛與上下車配對關係。

`local-audit.json` 記錄來源 SHA-256，供整合時確認來源版本。不得把同小時上車數當成一班乘客數，也不能將不同支線合成單一服務。

## 方法

1. 全庫只做 SQL 彙總。原型另以 `board_date >= 2025-01-01 AND board_date < 2025-02-01` 擷取一個月必要欄位到記憶體。這是上車日期窗口，跨月下車仍保留。
2. 排除缺失、倒序、零秒或超過六小時區間；將六小時視為可修改的品質檢查門檻，沒有宣稱它是業者規定。依既有站點地理順序推方向，同站與未知站不硬判。
3. 同一 vehicle、subroute、direction 的旅次按上車時間排序，以區間相交或間隔不超過門檻合併。比較 0、10、20、30 分鐘。跨午夜不強制切開；月界前已上車而窗口內才下車的旅次不在樣本內，所以首月界群組可能截斷。
4. 以半開區間 `[上車, 下車)` 的事件掃描計算同步配對票證峰值。同秒先下後上。其單位是同時有效的旅次區間數，不是小時人次。只有歸車與時間正確時，才可解釋為票證乘客車內人數代理。
5. 標記嚴格時間前進時的站序回退、候選跨度超過四小時、同車輛值不同支線或方向的重疊。站序回退依既有地理順序檢查，支線繞行、刷卡延遲都可能造成旗標，因此只作診斷，不自動校正。相同支線與方向的車輛值共用仍可能無法偵測。
6. 示範情境從零間隔、無上述旗標、至少 20 筆的候選中，挑同步峰值最高者。這是刻意挑出的高值個案，不能代表整月或全線平均。

若取得逐班實際發車時間與 GPS，應先將候選對照正式班次，再檢查到站次序、車輛識別一致性與誤配率。沒有這一步，報告中的「候選」不可在介面改名為「實際班次」。

### 有界策略模擬

選出示範候選為 2025-01-31、6670A、回程，69 筆配對旅次，跨度 178.1 分鐘，同步票證區間峰值 69。即使沒有診斷旗標，這個高值仍須先查核班次與車輛識別，不能據此宣稱實際超載。

容量缺失，採 30、40、50 作敏感度參數，額外車數為 0、1、2，共兩種分流政策、18 個情境。容量不是車隊實際規格。演算法介面另可接受其他正整數容量，額外車數限制 0 至 4。

- 全起點分流，允許所有既有旅次轉到假設平行車。
- 中段起點分流，只允許在候選已觀測站點範圍內部上車的旅次分流。「中段」不是正式全路線端點認證。

按照旅次區間長度優先、固定次排序的 first-fit 規則，在不超過額外車容量的前提下搬移整筆旅次；原候選峰值已低於或等於容量參數就停止搬移。保持原上下車站與時間，假設平行車同時提供相同站間服務。不增加成功搭乘數，不模擬未上車需求。這是確定性的可重現啟發式，沒有證明全域最優。

容量 40 的示範結果如下，完整 18 組在 `summary.json`。

| 政策 | 額外車數上限 | 移轉旅次 | 原車票證峰值 | 額外車票證峰值 |
| --- | ---: | ---: | ---: | --- |
| 維持原分配 | 0 | 0 | 69 | 無 |
| 全起點分流 | 1 | 29 | 40 | 29 |
| 中段起點分流 | 1 | 29 | 40 | 29 |
| 全起點分流 | 2 | 29 | 40 | 29、0 |
| 中段起點分流 | 2 | 29 | 40 | 29、0 |

兩種政策在此參數下同結果，只能說這一候選有足夠符合中段定義的旅次可分流。額外車數是上限，不代表已動用全部車輛。69/40 只能稱為配對票證峰值與情境容量的比值，不能稱實際載客率。此策略也不構成「提升載客率」的證據，增加車輛可能降低每車平均載客，仍須共同考慮服務、成本與排放。

缺少距離、實際班表、空駛、車庫、司機工時、非票證與訂位保留席，無法證明平行車能執行，也無法估營運成本、候車改善、拒載降低、旅客公里／容量公里或淨減碳。額外車出發位置未驗證，因此「中段分流」不能直接改稱可營運的「中間站起駛班表」。

## 驗證與重現

需要既有 Bun、已安裝的 `@libsql/client` 與 TypeScript。只有兩個資料庫腳本需要既有 `DATABASE_URL` 與 `DATABASE_TOKEN`，不要貼進報告或命令列。無須新增依賴。

```bash
bun scripts/lab/occupancy/probe.ts
bun scripts/lab/occupancy/analyze.ts
bun test src/features/lab/occupancy/model.test.ts
bun scripts/lab/occupancy/verify.ts
bun node_modules/typescript/bin/tsc --ignoreConfig --noEmit --skipLibCheck --module esnext --moduleResolution bundler --target es2022 --types bun src/features/lab/occupancy/model.ts src/features/lab/occupancy/model.test.ts scripts/lab/occupancy/analyze.ts scripts/lab/occupancy/probe.ts scripts/lab/occupancy/verify.ts
```

實際執行結果：兩個唯讀資料腳本結束碼 0；8 項單元與窮舉測試通過，0 失敗，4,633 次斷言。24 個月快取逐鍵核對 292,562 列通過；18 個情境的旅次與旅客秒數守恆、原候選峰值不增加、額外車容量不超過參數均通過。指定檔案 TypeScript 檢查結束碼 0。這些驗證不等於真實班表、車型或效果已驗證。

測試包含周轉旅次不可累加為同時載客、同時上下車、跨日、輸入順序、不同空檔門檻、站序逆行、無效參數、分流停止條件，另以 128 種區間子集合與容量／額外車組合檢查限制與守恆。

## 整合與後續

主代理可直接匯入 `src/features/lab/occupancy/model.ts` 的純函式，或載入 `/data/lab/occupancy/summary.json` 顯示既有結果。UI 設計與路由由主代理安排 Claude；此交付完全沒有 UI。若呈現數字，應同時顯示候選未驗證、資料月份、容量為參數、缺少非票證與未上車需求等說明，不可將峰值比改成真實載客率。

下一步優先補營運方的歷史班次與車輛唯一識別映射、逐班合法可用座位及訂位保留席，抽樣對照 GPS。通過歸班驗證後才擴展全期間或計算旅客公里／容量公里。要評估中間站服務，另需排隊、拒載或人工抽樣，不能從成功刷卡者反推完整需求。
