## 三、審查 `alert/v5/run.py`

### 3.1 可重現性（事實）
- 以原始碼與唯讀 `trips.db` 重跑，`metrics.json` 與 `dashboard_data.json` 與 repo 版本**逐欄比對差異 0**。
- 計數：`trips_raw` 1,800,910、`rides_used` 1,786,330、78,112 班、414,232 列、訓練 254,722／選擇 53,153／留出 106,357、留出 19,894 班，皆與 README 相符。
- 留出期日數：README 寫 183 日（2025-07-07 無刷卡），`forecast/v2` 寫 184 日（日曆日）。兩者定義不同，計畫書不寫日數即可避免衝突。

### 3.2 洩漏檢查（事實：未發現目標洩漏）
- **特徵**：`up_load`、`minute`、`dow`、`rest`、`subi`、`dir`、`u`、`s`、`k`、`dist`。除 `up_load` 外皆為靜態或離站前可得；`up_load` 只用 `bt ≤ t_dep` 與 `alight_ts > t_dep`，即離站當下的在車狀態。在即時系統中，需要該時點之前的下車刷卡已上傳（已在計畫書「上線需補」列出）。
- **服務站**：只用訓練期計數（第 27–29 行）。
- **門檻與早停**：早停與門檻只用驗證期（`va`）；基線「先驗」與「查表」只用訓練期（第 85 行 `_t = R[tr]`）。留出期只用於報告與日重抽。
- **班次與方向**：`dir = sign(ao − bo)` 由下車站推定，班次切分也依此方向（README 限制 1 已揭露）。這是**回顧性**資訊，在即時系統中需改由班表或路線方向定義。README 限制 1 已說明，計畫書 §5.4 也寫了，足夠。
- **標籤**：`ld` 含同班次中在 s 之前上車、s 之後才下車者（第 51 行），是事後真值，合理。
- **旅次篩選**（`alight − board ∈ [3 分, 4 小時]`，第 21 行）以下車時間篩選，屬事後條件。影響比例小，計畫書已揭露。
- 小瑕疵：第 58 行 `R = R[R.up_load > 0]` 實際上是 no-op，因為只要有人在 u 站上車，`up ≥ 1`；保留無害，但讀者會誤以為是過濾。

### 3.3 母體（服務站集合）是否合理（事實＋推論）
- **合理**：服務站由訓練期刷卡推得，不用留出期資訊；6670H 只有 4 站，與營運直覺一致。
- **【事實】** 「k」是「服務站中的第 k 個下游站」（第 49 行先過濾服務站再取前 3），**不是實體第 k 個中途站**。計畫書 §2.2(2) 寫「其後前 3 個中途站」，與程式不一致，應改為「該子路線實際服務的下游前 3 站」。
- **【事實】** 目標是「任一」站達門檻（第 67 行 `y=max`）。計畫書 §2.2(2) 寫「該離站點自己的前 3 個中途站確實達門檻」，讀者會理解為「全部」或「任一」兩種意思。應明寫「任一」，並同時報逐站 k 的數字（k=1 精確率 87%、k=2 75%、k=3 74%），否則 99% 會被誤讀為「每一站都準」。
- **【事實】** 母體只含「有人上車的 (run, u)」。沒有人上車的離站點不在列內。計畫書在 §2.2(2) 有寫「每班車在每個『有人刷卡上車的站』離站時」，但 §5.4 的風險與限制沒有列出；涵蓋率的分母也只含這些列。建議列入限制。
- **【事實】** 列數從 v4 的 487,146 降到 414,232（−15%），不是 40%。原因是 v5 改為取「下一個服務站」，而非「剔除不可能的站」，所以目標站的實體位置變遠了（例如 6670H 的目標 k 可能跨過數站）。計畫書與儀表板寫「剔除 40% 結構上不可能的目標」容易被理解為「只是刪掉」，應改寫為「改取該子路線的下游服務站」。
- **【事實】** 班次間隔預設 60 分（`GAP=60`）。`TASK-COMMON` 第 1 點規定 90 分，README 未說明偏離原因。另外 TASK-COMMON 要求在 README 報告「每 run 平均停靠數」與「與到站列加總的吻合度」，兩者 v5 README 都沒有報。此外，有 24,816／42,693＝58% 的車日方向群組被切成多班，切分規則的影響很大，所以 30／120 的敏感度是必要的（見 3.6）。

### 3.4 特徵與標籤是否一致（事實）
- `up`：離站 u 站後（含 u 站上車者）的在車人數，時點為 `t_dep`（u 站最後一筆上車）。
- `load`（標籤）：到達 s 站、下車後、上車前的在車人數（不含 s 站上車者與 s 站下車者）。
- 兩者定義**連續一致**：u 站離站後的在車人數，即為下一站上車前的在車人數（扣除途中下車者，加上途中上車者，並於標籤中計入）。這與計畫書表 1 的「分母（上車前車上已有乘客）」概念一致。
- 因此「`up` 與 `load` 同班次定義」的修正是正確的。

### 3.5 評估是否公平（事實＋推論）

**(a) headline 的提示量不一致（重要）**
- README 的「每日提示預算」表（41 席座位不多）：N=5 時模型 2.87 次／日、R 2.02、查表 3.27、先驗 3.13。涵蓋分別為 23.7%、16.3%、26.5%、8.3%。**四者實際提示量不同**。
- 計畫書摘要寫「模型的提示 99% 正確、涵蓋 24%（規則 R 16%、查表 27%）」。數字正確，但 R 只用了 2.0 次／日、模型用 2.9 次／日，不是同預算比較。
- 相近提示量的矩陣（`matched_volume`，41 席）：
  - 約 4.2–4.6 次／日：模型 4.22 次、涵蓋 34.9%、精確率 99.2%；查表 4.58 次、涵蓋 **37.3%**、精確率 97.7%。
  - 即同量下，**查表涵蓋較高、模型精確率較高**。
- 37 席，約 4.2–4.3 次／日：模型涵蓋 44.0%、精確率 99.4%；查表 42.6%、97.8%。這裡模型涵蓋略高。
- 結論（推論）：模型相對查表的優勢主要在精確率，且在 41 席情境下涵蓋並不更高；headline 應改用同量比較或同時報兩者。

**(b) matched 表的網格有缺陷（事實）**
- `curve()` 的掃描點是 `np.quantile(A.sc, np.linspace(0.40, 0.9999, 60))`，只有 60 個點，且查表與 R 的分數大量同值（ties）。
- 結果：41 席的查表在 2 與 3 次／日欄位都輸出 **4.585**（不是 2 或 3）；R 在 2 與 3 次／日都輸出 2.339。這表示 `matched_volume` 的「2、3 次」格**不是匹配值**，而是最近網格點。
- `at_volume()` 取最近點，沒有警示。README 與計畫書把這一格當作「相近提示量」，需修正或加註。

**(c) 「相同每日提示預算」的說法不成立（事實）**
- `dashboard/template.html` 第 81 行寫「四種方法在相同每日提示預算下比較」。實際 N=5 的量為 2.87／2.02／3.27／3.13，不同。計畫書 §2.2(2) 在表後寫「規則 R，門檻調至相同預算：1.0／2.0／6.1 次」，這一句比儀表板誠實，但「相同預算」一詞仍不準確。

**(d) 「660 筆」的統計口徑錯誤（事實）**
- README 寫「模型 N=5 的正確提示（660 筆）多為短站間」。`lead_pairs_model_N5`（第 137 行）是用 `first_flag` 的**未套每日上限**的首次提示，只取正確者，合計 660。
- 套 N=5 上限後的正確提示約為 `2.87 × 183 × 0.9905 ≈ 520`（由表值推得，未直接計數）。
- 站對表的比例（埔里→崎下 334、日月潭→日月老茶廠 117 等）應說明是未套上限的口徑，或改用套上限後的計數。

**(e) 提前量是條件統計（事實）**
- 提前量只取「正確提示」（第 127 行、第 137 行）。這符合「提前量是正確提示的性質」的解讀，但計畫書 §2.2(2) 寫「N=5 時提示的提前量中位數約 3–5 分鐘」，沒有寫「正確提示」，讀者會以為是所有提示。應加入。
- 提前量由站間直線距離 ÷ 固定速度得到，且 README 寫明是近似（限制 3）。
- 站對表顯示，多數提示是埔里站→崎下（2.2 km）與日月潭→日月老茶廠（3.3 km）等短站間；高鐵臺中站→桃米坑（37 km）只有 59 筆（未套上限）。因此「提前量中位數 3–5 分鐘」基本是站對幾何的性質，**不是模型能力**（這正是第 41 輪的意見，計畫書仍大致保留，建議把「站對表」放在正文）。

**(f) 基線與區間（事實）**
- 規則 R 有兩種門檻：曲線與逐站表用固定 `up ≥ 席數−5`（第 77 行起的 `for kind, thr` 迴圈，`few`＝席數−5），每日預算表用分數分位數以符合預算。README 限制 6 已揭露，足夠。
- 區間：固定門檻指標用日重抽 200 次（95%）。**每日預算表與提前量沒有區間**，計畫書的「N=3／5／10 的涵蓋」因此沒有不確定性。
- 留出期 19,894 班、183 日，樣本量足夠；但 `ops` 的 N=3 每日只有約 1.4 次提示，涵蓋的標準誤較大，建議報區間。

**(g) 校準（事實）**
- `calibration` 的十分位在 41 席：最高十分位平均分數 0.599、觀察率 0.564；其餘多為 0。計畫書未提校準，這是合理的省略，但若要說「分數可解讀為機率」，只能說頂端大致校準，中段沒有樣本。

### 3.6 班次切分敏感度（已重跑，見第六節）
- 計畫書 §2.2(2) 寫「班次切分間隔取 30／60／120 分，結果穩定」。經查，`alert/v5/out/` 只有 60 分的輸出；30／120 分的穩定性證據是 **v4**（`alert/v4/sens_gap30`、`sens_gap120`）。
- 本輪以 v5 `run.py` 重跑 30 與 120 分（輸出於 `…/scratchpad/rerun/gap30/`、`…/scratchpad/rerun/gap120/`）。結論：**N=5 的精確率與涵蓋排序穩定，但班次數、盛行率與模型相對查表的精確率差距不穩定**，「結果穩定」一句需改寫。

## 五、評分與各面向的補強方案

### 5.1 完整性：7.3（離 8.5 還差 1.2）
**扣分理由**（事實）：
- 第七節列出的高、中嚴重度問題（數字口徑、G1 來源、33 次與 Q0 的風險表述）。其中 headline 的 99%／24%／16% 比較（3.5(a)）與「相同預算」用語，是讀者最容易誤讀的地方。
- 班次敏感度已對 v5 重跑（第六節），「結果穩定」只在部分指標成立。TASK-COMMON 規定的「平均停靠數」與「到站列加總吻合度」未報（3.3）。
- 「10 人／次留站」假設沒有引用既有的溢出證據（`drafts/spillover-experiment-v3.1.zh-TW.md`），而該草稿提供了可用的數量級（見 5.2 的第 3 項）。
- 計畫書引用的 G1 0.4%／1.6% 與 69 個休息日沒有可追溯的算式（第四節）。
- 表格字級 10.5–11 pt（主文 12 pt 符合；若官方規定涵蓋表格需確認）。

**文件層面可補（只靠既有數字即可）**：
1. 統一 headline：摘要與 §2.2(2) 的 N=5 比較改為「同量」比較（用 `matched_volume` 修正網格後的值），或同時報三者的實際量。
2. 把「任一站」與逐站 k 並列，寫明 k 是「服務站序」。
3. 加一個術語表（R、查表、先驗、k、any-of-3、WAPE、Clopper–Pearson、G0–G3）與一頁調度員版（第六節）。
4. 補上 TASK-COMMON 要求的 run 統計（平均停靠數、與到站列加總的吻合度）與 GAP=60 vs 90 的說明。
5. 將「被留下」的 10 人假設改為情境區間，引用溢出 v3.1 的數量級（見 5.2 第 3 項）。

**離 8.5 的天花板**：約 8.0–8.5。這是四面向中唯一能靠文件與重算補到的面向，前提是每一項數字都能追到檔案與行號。

### 5.2 可行性：6.8（離 8.5 還差 1.7）
**扣分理由**（事實）：
- 回測與儀表板可重現（事實），但**沒有即時資料路徑的驗證**。上游離站即時刷卡、車機上傳延遲、下車刷卡是否即時可得，全部是外部問題，計畫書已列為「上線需補」，但沒有延遲預算。
- **沒有缺漏或延遲的穩健性測試**。計畫書的「3 分鐘資料新鮮度」是設計假設（§2.5），沒有以資料模擬驗證。
- G1(b) 的「顯示有座位」定義未寫清（系統用哪個門檻？與 41／37 席的對應？），0.4%／1.6% 的來源未找到。

**文件層面可補（已能做，有資料）**：
1. **缺漏與延遲的穩健性測試**（推薦優先）。方法：隨機丟棄 10%、20% 的下車刷卡（同時對訓練與測試，以及只對測試），或把下車時間延後 3 分鐘，重算 41 席 N=5 的精確率、涵蓋、每日提示量，與查表、R 比較。
   - 預期產出：一張表（丟棄率 × 方法 × 指標）。
   - 可行性：以 `run.py` 加參數即可，約 2–4 小時（含重跑）。
   - 外部：真實的丟棄率與延遲分布需與票證商確認；本測試只給敏感度，不能替代。
2. **延遲預算表**：把「上車刷卡 → 車機上傳 → 雲端 → 儀表板 → 站牌」每段的假設延遲列出，並說明 3 分鐘門檻在什麼延遲下會開始誤報「資料不足」。
3. **G1(b) 定義**：寫明「顯示有座位」由哪個分數與門檻決定，並重算 0.4%／1.6% 或改用可重算的數字。

**只能靠外部資料的部分**：
- 即時上游離站刷卡與車機延遲（需南投客運與票證商）。
- 車碼對車型（41／37 席）。計畫書已用兩種情境，這是合理的誠實逼近，不要宣稱已識別。
- 班表與計畫時刻（目前的班次是刷卡推得，無法對照班表）。

**離 8.5 的天花板**：約 7.5–8.0。要到 8.5，需要真實資料的影子運行或即時介接的展示，這在 5 天內不可能。

### 5.3 創新性：6.4（離 8.5 還差 2.1）
**現況**（推論）：方法組合（服務站集合、同班次定義、查表、LightGBM、每日上限、碳平衡門檻、閘門式停止）有條理，且計畫書誠實宣告「不主張首創」，這一點是加分。但每一項都是標準做法，評審不容易給高分。

**可以補的（已有資料）**：
1. **溢出量級的上界**（推薦，見下方算術）。把溢出 v3.1 的「合格後車事件的超額上車」當作上界，取代 10 人假設。這一步不是新方法，但它把一個無依據的假設換成有來源的範圍，並使結論對假設不敏感。
2. **「站點 × 時段」的站務行動建議**：從熱點與提前量的站對表，挑 1–2 個站對，寫出「提示後站務做什麼、客服如何回覆」，並說明評估方法（G1 的哪一條件）。

**溢出上界算術（我的計算，事實＋假設）**：
- 41 席：前 10 窗口每窗口每日座位不多事件 0.087–0.386（留出期，以日類分母重算，與 dispatch 相符）。
- 溢出 v3.1 的「每合格後車事件超額上車」：約 0.41–1.22（站別前 10%）與 1.82–2.58（38／43 席情境）。
- 乘積：每窗口每日超額上車 **約 0.04–1.0 人**。若一班加開車吸收全部，每班預期 ≤1.0 人；若吸收一半，≤0.5 人。
- 37 席：每窗口每日事件 0.230–0.860，乘積約 0.09–2.2 人。
- 碳平衡點 24–32 人（80 車公里）。即使取溢出上界，**仍遠低於門檻**（41 席約 4%、37 席約 9%）。
- 注意（事實）：v3.1 用的是 38／43 席情境（不是 37／41），且 v3.1 明載「不能解讀為留站人數或因果效果」，反方向對照也為正。因此這只能當**量級上界檢查**，不能寫成估計。計畫書引用時必須同時寫明這些限制。

**只能靠外部資料的部分**：真正的被留下人數（需 G0 現場計數）；是否因溢出而實際改搭下一班。

**離 8.5 的天花板**：約 7.0–7.5。方法本身是標準做法，原創性需要現場驗證才有說服力，而這在 5 天內做不到。

### 5.4 影響力：6.9（離 8.5 還差 1.6）
**扣分理由**（事實）：
- 所有效益是情境（§5.3）。「可量化的已知效益」只有熱點集中與碳門檻，這是「不做什麼」的效益，不是「做了什麼」的效益。
- 缺一個可量化、可執行的建議。計畫書說「預警適合通知下一站站務與客服」，但沒有寫明站、時段、每日次數與預期覆蓋。
- 3–5 分鐘的提前量與「提示量上限 5 次／日」意味著提示只能影響下一站，計畫書已誠實寫明，但也因此影響力被壓低。

**可補的（已有資料）**：
1. **資訊覆蓋指標**（推薦）：對 N=5 的每個提示，計算其後同班次在提示站之後上車的旅次數（即可能收到「下一班或下一站資訊」的人）。每日加總，報中位數與區間。這不是效果，但能回答「提示會接觸多少人」。
   - 可行性：`run.py` 的 `rows` 已有 `rid`、`t`、`u`，只需加一個計數，約 1–2 小時。
2. **一個站點、時段的具體建議**：例如 6670A 休息日 16–17 時、暨南大學校內（有 21% 座位不多）。寫明：提示次數、提前量、站務動作、評估方法（G1 的哪一條件）、停止條件。
3. **加班的決策上界**：把第 5.2 第 3 項的溢出上界寫入 §2.3，說明即使取上界，每班預期仍遠低於 24–32 人，因此「固定加班」不建議，但「資訊與站務」可優先。這是對影響力最直接的加分。

**只能靠外部資料的部分**：提示後實際改變的旅次（需現場）、客服工時（需 G0 估計）、長者與無障礙乘客的實際影響（需訪談）。

**離 8.5 的天花板**：約 7.5。效益本質上是情境，除非有 G0／G1 的現場數字，否則評審很難給 8.5 以上。

1. **穩定，可以寫**：N=5 的模型提示精確率約 99%、每日提示約 2.9 次、涵蓋約 24–25%；涵蓋排序在三種間隔下都是「查表 ≥ 模型 > 規則 R」；提前量中位數 3.2 分，且 ≥10 分比例約 14%。提前量中位數的穩定，是因為它由少數站對的距離主導（埔里→崎下、日月潭→日月老茶廠），不是模型穩定。
2. **不穩定，計畫書需改寫**：
   - 班次數在 73,829–97,470 之間（相對 60 分為 −5% 至 +25%）。班次定義本身對結果有影響，「結果穩定」只能指指標，不能指班次。
   - 盛行率 5.6–6.4%；計畫書寫的 6.2% 只對 60 分成立。
   - 模型相對查表的精確率差距為 **2.9、6.6、6.7 個百分點**。計畫書 §2.2(2) 寫「只高 6.6 個百分點、召回相同」，只對 60 分成立。召回差距為 −0.6 至 +2.2 點，方向不一。
3. **同量比較仍有網格問題**（3.5(b)）：三種間隔下，查表在 `matched_volume` 的最近點分別落在 5.74、4.58、4.58 次／日，模型約在 4.2 次／日，因此 matched 表的涵蓋數字不能嚴格比較，只能看 N=5 的實際量。
4. **建議改寫（計畫書 §2.2(2)）**：「在班次間隔 30／60／120 分下，N=5 的模型精確率為 99%、涵蓋 24–25%，查表涵蓋 26–27%、規則 R 16%；班次數與模型相對查表的精確率差距（3–7 個百分點）隨切分變動。」

## 八、南投客運調度／營運人員視角

**1. 實用性（推論）**
- 調度員會問三件事：今天哪一班、哪一站會不夠坐、我能做什麼。計畫書 §2.4 的「營運現場一天」已回答前兩件，第三件（「我能做什麼」）偏弱：提前量 3–5 分鐘只能通知下一站站務或客服，不能派車，這點計畫書已寫明。
- N=3–5 時每日提示 1.4–2.9 次（N=5 時休息日約 3.6 次、上班日約 2.6 次），對調度員可承受，但**需要一個預設的動作表**：例如「收到提示後，站務在 X 分鐘內確認、客服用哪段話術、何時升級給調度」。目前只有「調度員決定」，沒有動作表。
- 對調度員而言最有用的可能不是預警，而是「固定時段的站務與客服配置」（熱點窗口），這一點計畫書有提到（§2.3 低成本行動），應放在更前面。

**2. 看得懂嗎（事實）**
- 術語密度過高：R、查表、先驗、k、any-of-3、WAPE、Clopper–Pearson、G0–G3、窗口。調度員讀完 §2.2(2) 的表 2 與文字，很難回答「我該信多少」。
- 建議：在正文開頭加一頁「怎麼讀這份計畫」，只用三個數字（每日提示次數、正確率、涵蓋率）與一個例子（dashboard 的歷史回放）。

**3. 是否會被讀成指控（事實＋推論）**
- **高風險**：Q0（票務異常、金額、可退款）。即使有「不代表錯扣」，這在營運人員眼中是「你們的票有問題」，與命題（智慧營運決策）的距離很遠。建議移到附錄，或刪除。
- **高風險**：§1.3「33 次 ≥50 人」與 §5.4 的同一句。這句話的語意是「超載」，即使有「不判定」，仍會被讀成指控。建議改為「資料品質：33 次到站的重建載客超過席位加站位，需與車型對照核對」，且不寫「官方座位加站位約 49–50 人」的對照。
- **中風險**：§1.2 的「推估座位已滿」欄位與「座位不多」欄位，會讓讀者以為是在說「該站上車的人沒有座位」。建議欄位名改為「上車前載客達席數（代理）」與「上車前載客達席數減 5（代理）」，並在表上方寫「不是乘客被拒絕的證據」。
- **中風險**：§2.3「固定加班缺乏觀察資料的支持」一句，對 6670D／6670H 的既有預排會被讀成間接批評。計畫書已加限定語，但建議在同一段再寫一次「不評價既有排班，只說明新增固定專車的證據不足」。
- **低風險**：§4.1 引用南投客運官網「埔里往高鐵尖峰常客滿」，計畫書已標明為「搜尋索引所見，原頁未能直接核對」，這樣處理是對的。

**4. 有沒有可能被用來對付業者（推論）**
- 「每班緩解 0.01–0.6 人次」與「碳平衡點 24–32」合在一起，對業者是「不加班」的理由，這是有利於業者的結論，但計畫書也寫明「不作為業者績效考核」。這一點應維持。
- 司機不作績效考核（§3）：正確，且應在 KPI 表中也寫明。

## 九、直接回答：四項都能到 8.5 以上嗎？

**不能，以現有資料與誠實原則，我的判斷是四項都到 8.5 以上做不到。**

| 面向 | 我認為的天花板 | 原因 |
|---|---:|---|
| 完整性 | 8.0–8.5 | 唯一能靠文件與重算補到的面向。前提是修正第七節的 8 處不一致、補上班次敏感度、統一口徑，並讓每個數字可追到檔案。 |
| 可行性 | 7.5–8.0 | 需要真實即時資料或影子運行才能到 8.5；在 5 天內只能做穩健性測試與延遲預算，無法替代外部驗證。 |
| 創新性 | 7.0–7.5 | 方法組合清楚，但單項皆為標準做法；唯一有原創性的溢出簽章仍是探索性，需要 G0 的現場結果才能提升。 |
| 影響力 | 7.5 | 效益本質上是情境（§5.3）。加入「資訊覆蓋」與「溢出上界」可以把「不要加班」的結論變得更扎實，但「提示救到了多少人」只能靠現場。 |

**最可能的天花板與原因**（推論）：計畫書的核心誠實性（不宣稱效益、不宣稱首創、不宣稱即時可用）會限制影響力與創新性的分數。評審若重視「可在 T0 後直接執行」，這份計畫書只能給到約 7.5。要突破，需要 G0 的現場結果，而目前的 T0 是「南投客運同意之日」，時間上不可能在初賽前完成。

**對使用者目標（四項皆 >8.5）的建議**：不必硬追四項。優先做完整性與可行性的文件層面補強（可在 5 天內完成），並把影響力的「資訊覆蓋」與「溢出上界」寫入。（推論）這樣四項合計可以從 6.9 提升到約 7.5，但不會全部到 8.5。
