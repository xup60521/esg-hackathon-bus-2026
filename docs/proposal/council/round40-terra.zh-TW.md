## 第 39 輪重點逐項核對

1. 【事實】v3 用地理 order 而非 board_seq，且固定選前 3 個中途站，不再以「下游有人上車」選目標。方向仍取每筆旅次事後上下車站之差，班次依完整資料切分；不能因此說整條管線沒有未來資訊。未驗證各子路線實際行經這 3 站，固定地理站序可能產生不行經的候選站。
2. 【事實】上游載客 `after` 以整個事後重建 run 的上、下車站序計數，並未以 `board_ts <= t_dep` 過濾。若同一重建 run 因切班錯誤或站序倒退包含日後在同站／上游站上車的紀錄，就會帶入未來上車；run 是否成立本身亦需後續資料確認。下車站在刷卡資料中到下車才記錄，不能未加條件稱所有輸入即時可得；實務上可由即時上下車計數維護載客，但這尚未驗證。資料篩選使用完整乘車時間 180–14400 秒，亦為事後條件。
3. 【事實】站點目標 `bo < s and ao > s` 在站序和班次正確、完整刷卡及先下車後上車的假設下，是離開 s 之前、下車之後且上車之前的刷卡可見載客；不是「實際在車人數」的全面觀測。它包含上游後至 s 前的新上車者，作為事後標籤可以，但車型、現金、漏刷與不行經站仍未知。`u` 只取有上車站，零載客上游亦排除，結果不能代表所有出站。
4. 【事實】程式雖建立 78,112 個 run，後續 `run_frame` 以車碼、日期、方向、站分組，並以車碼、日期、方向作提示與正例單位，沒有 run ID。同車同日同方向多班會被合併；同站的 `t=first` 配上跨班最大分數與標籤，更可能把較晚班的結果放到較早時間。13.13 及所謂班次涵蓋率、G1 天數因此不是可靠班次統計。這是新版必修錯誤。
5. 【事實】`flags` 把首次達門檻時間 `tf` 和該車日方向**任何**達門檻且正例的時間 `tc` 合併，即使首次提示後預告的三站沒有達標、稍後另一離站才達標，仍算正確；甚至跨重建班次。其 99% 精確率不是首次提示的命中率。`dmin` 是各離站候選站的最短距離，未綁定首次提示、命中站或發生時間；提前 ≥10 分鐘比例與中位數不能作為該提示提前量。應保存首次提示的三個具體目標、匹配首個達標站，未命中即錯報，並以相同 run ID 計算。
6. 【事實】每日按時間順序封頂確有實作，但共同上限不是相同實際提示數。N=5 模型平均 2.77／日，R 2.19，先驗 2.59；N=3 分別 1.68、1.15、1.54；N=10 分別 6.57、6.22、7.86。門檻依選擇期未截斷的平均提示量選擇，而留出期再截斷；因此不能將涵蓋差異全部歸因模型較好。R 在預算比較用 42 等載客門檻，而逐站表用 36，兩者應明示。固定共同上限仍可回答資源限制問題，但應另配對實際提示量或畫精確率／召回與提示量曲線，並報每方法實際量及日分布。
7. 【事實】最後刷卡時間只是事後離站代理，須等未來才知道它是最後一筆；以直線距離÷0.7 km／分是情境，不是實測旅行時間，42 km/h 對山區並無本報可核實的保守性證據。現有 PDF 未寫 0.7、直線距離，且把推算提前量寫成提示可提前，揭露不足。更重要的是上一點使目前提前量統計本身未對應提示，先修程式再談速度敏感度。
8. 【事實】PDF 已改「固定加班缺乏觀察資料支持」、不評價既有 6670D/H、無障礙約束、八個連假範圍；dispatch/v3 README 已存在。摘要仍稱「結論可直接用於調度」，與 §5.4 不直接上線矛盾；§4.2、§5.3 和結語仍稱避免不划算加班，超出可觀察證據。§2.4 仍寫「模型機率」，與未校準分數的謹慎表述不一致。未操作儀表板，無法確認所有互動或文案已一致。

## 剩餘五天：要做完並留下可驗證成果

以下是加分條件，不是已完成成果。以結果替換既有泛用案例或重複文字，保留十頁上限。

- **完整性，目標 >8.5。** 現有 SQLite、地理站及班次程式可做事件漏斗與時間稽核：保存篩選前後筆數、站序與路線交集、同車日方向多 run 比率、三個匿名案例的上車／下車／離站時間，逐欄標記當時可得性；修正所有摘要與 G3 不一致並附重跑結果。真實停靠與站序需班表／GPS 核實；無外部資料時對疑似不行經站做排除及上下界敏感度，不把它稱實際路線。
- **可行性，目標 >8.5。** 為每個重建 run 保留唯一 ID，載客只用時點前上車與已知下車，重新定義首次提示匹配、提前量及錯報，保存逐筆提示、三站標籤與每日摘要；對切班間隔和離站代理做敏感度。現有資料可跑離線回測並用實際觀察站時間作有限檢查；真實離站、即時延遲及無刷卡經站仍需車機 GPS 和現場觀察。若修正後結果較差，照實報告；離線重播不能當作現場通過 G1。
- **創新性，目標 >8.5。** 用修正後同一批留出事件，完成 R、歷史先驗、模型及模型結合熱點的逐日回放；在 N=3／5／10 共同硬上限之外，配對實際提示量，列命中、漏報、每日至少提前 10 分鐘的有效命中及工作量。保存可重現程式與逐日檔，挑一個案例展示調度員何時知道什麼、能做什麼。現有資料可完成代理回放；實際操作節省工時須調度員試用量測。
- **影響力，目標 >8.5。** 依日期、方向及連假／一般休息日列熱點分布，模擬固定與條件觸發的車次、成本、可見乘客與不同未上車人數；另以自用車轉乘比例和里程獨立計碳。保存情境表與程式，標示假設而非實績。車型對照、整班車輛可用性、無障礙需求、未上車人數和乘客轉乘來源均須外部資料；可用多組限制範圍展示哪些情況才值得現場檢驗，不能宣稱真實節省或減碳。

【推論】南投客運調度員能理解方向、站點與需通知誰；但現在缺可靠的班次辨識、目標站及可執行提前時間，不能據 99% 安排機動車。尊重既有排班的新增聲明有幫助；摘要與 ESG 的「不划算」仍可能被讀成否定既有加班，應一致改成資料不足以判斷，並保留服務、安全及無障礙考量。
